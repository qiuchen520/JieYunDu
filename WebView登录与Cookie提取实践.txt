================================================================
WebView 登录 + 登录态 Cookie 提取：通用实践原理
================================================================
适用场景：App 内嵌网页让用户手动登录，登录完成后由 App 自动抓取
          登录态凭证（Cookie / Token），持久化后供后续接口调用。
本文只描述「怎么做才对」的通用工程实践，不含任何具体项目的代码。
================================================================


一、总体流程
----------------------------------------------------------------
1) 打开登录页  ：用 WebView 加载目标站点的官网登录页，用户手动登录
                 （扫码 / 账密 / 短信验证码都由页面自己处理）。
2) 轮询取凭证  ：登录完成后，页面侧会出现登录态 Cookie（或 localStorage Token）。
                 App 周期性读取该凭证。
3) 廉价预检    ：先用「关键字段是否齐全」做一次零成本判断，
                 挡掉登录过程中的临时态、初始化态。
4) 网络校验    ：真正发一次轻量接口请求，确认这份凭证确实有效。
                 这是区分「Cookie 出现了」和「登录真的成功了」的唯一手段。
5) 落库        ：校验通过后持久化（建议加密），并标记该平台为已登录。
6) 关闭登录页  ：回调上层，销毁 WebView。
7) 保活        ：后续按有效期刷新 / 合并回写凭证，退出时清理。

核心认知（最重要的一条）：
    「Cookie 出现」≠「登录成功」。
    登录过程中页面会写入临时凭证；凭证也可能已过期。
    必须经过一次真实网络校验，才能判定登录成功。


二、WebView 的配置要点
----------------------------------------------------------------
1) 必开：
   - javaScriptEnabled = true    （登录页基本都靠 JS）
   - domStorageEnabled  = true    （localStorage / sessionStorage）

2) 建议开（否则页面基本没法用）：
   - setSupportZoom(true)
   - builtInZoomControls = true
   - displayZoomControls = false   （保留手势，隐藏屏幕缩放按钮）
   - useWideViewPort = true
   - loadWithOverviewMode = true

3) 显式设置 User-Agent：
   - 必须设成「该站点桌面网页版」的 UA，而不是 App 的默认 UA。
   - 原因：不设的话 WebView 会用系统默认（通常是 Android 移动版 UA），
     登录页会切到移动版甚至拒绝服务；而且登录用的 UA 与后续调接口
     用的 UA 不一致时，容易被风控判定为异常。
   - 原则：登录页用「网页 UA」，调接口用「客户端/API UA」，两者分属不同环节。

4) 桌面版页面适配（可选但常需要）：
   - layoutAlgorithm = NARROW_COLUMNS
   - setInitialScale(0)
   - 若页面没有 viewport meta 或限制了缩放，可在 onPageFinished 里用
     evaluateJavascript 注入/覆盖 viewport meta（允许缩放 + 适配宽度）。
   - 不加这一步，桌面版登录页在手机上会又小又不能缩放，用户没法操作。

5) Cookie 开关：
   - setAcceptCookie(true)
   - setAcceptThirdPartyCookies(webView, true)
     （登录常涉及第三方域/子域，不开可能读不到）

6) 生命周期：
   - 页面销毁时必须 webView.destroy()，否则泄漏。
   - 加载状态用 WebViewClient.onPageStarted / onPageFinished 驱动 loading UI。
   - 返回键要接管（保存过程中禁用返回，避免半途销毁）。


三、Cookie 的读取途径
----------------------------------------------------------------
3.1 主途径：CookieManager.getCookie(url)
   - 这是原生 API，能读到 HttpOnly 的 Cookie。
     （HttpOnly 只限制 JavaScript 的 document.cookie，不限制原生 API。）
   - getCookie 是「按 URL 取」，所以一个平台可能分布在多个子域上，
     要准备一个「URL 列表」依次读取，再按 Cookie 名去重合并。
   - 例：登录域、业务 API 域、下载/CDN 域可能各有一份。

3.2 兜底途径：拦截 WebView 实际发出的请求头
   - 实现 WebViewClient.shouldInterceptRequest，读 requestHeaders["Cookie"]。
   - 这同样包含 HttpOnly 的 Cookie，作为主途径失手时的补充。
   - 注意：
     * 该回调在工作线程调用，不是 UI 线程；
     * 回写采集结果必须用线程安全容器（如 AtomicReference）；
     * 命中判断按 host 过滤（host == 域 或 host.endsWith("." + 域)）；
     * 必须返回 null，让请求正常继续，绝不能阻断。

3.3 合并规则
   - 按 Cookie 名去重，后读到的覆盖先读到的（保持插入顺序）。
   - 输出形如 "a=1; b=2"，分隔符固定 "; "，名值分隔用第一个 '='。
   - 解析时要跳过无 '=' 或名字为空的脏片段。

3.4 线程与时机
   - CookieManager 相关调用建议在主线程或 WebView 创建线程上执行。
   - 轮询用协程 delay，不要阻塞主线程。


四、凭证有效性判定：两级判断
----------------------------------------------------------------
4.1 第一级：廉价预检（零网络成本）
   - 判断关键字段是否「齐全」，不判断是否有效。
   - 这一级的作用是挡掉：还没登录、登录进行中、页面初始化的中间态。
   - 判定语义必须写清楚是「任一命中」还是「必须全部命中」——
     这个语义写错是常见事故源头：
       * 有的平台要求 A 和 B 同时存在才算登录态；
         写成「任一命中」会把只有 A 的中间态误判成已登录。
       * 有的平台只需要一个字段（如 BDUSS 类）；
         写成「必须全有」则永远判定不了。
   - 所以：每个平台单独定义判定规则，不要用一套通用逻辑硬套。

4.2 第二级：网络校验（关键，不可省）
   - 拿凭证调一个「轻量、只读」的接口（例如取昵称/取账号信息）。
   - 返回成功 → 凭证有效，登录成立。
   - 返回失败 → 视为登录中间态或凭证无效，不报错、不弹错，
     继续轮询等待真正的登录态（或者在手动模式下提示用户重试）。
   - 必须与「手动保存」按钮走同一个校验入口，避免两套逻辑不一致。

4.3 校验失败后不要立刻重打
   - 记住「最近一次失败的凭证原文 + 失败时间」。
   - 相同凭证在短时间内不重复校验（等凭证变化或超时后再试）。
   - 这样网络闪断恢复后能自动补登，又不会疯狂重试。


五、自动检测循环的参数设计
----------------------------------------------------------------
建议用三个时间常量把行为钉死：

  轮询间隔         POLL_MS                 建议 1500ms
  真实校验最小间隔  VALIDATE_THROTTLE_MS    建议 5000ms
  同凭证重试间隔    SAME_CREDENTIAL_RETRY_MS 建议 10000ms

循环伪逻辑：
  每 POLL_MS 检查一次
    - 已结束 / 被暂停 → 跳过
    - 读凭证（读失败当空处理，不要抛）
    - 凭证为空 或 过不了廉价预检 → 跳过
    - 与上次失败的凭证相同 且 距失败 < 同凭证重试间隔 → 跳过
    - 距上次真实校验 < 校验节流间隔 → 跳过
    - 上锁（标记"校验在途"）→ 发网络校验
        · 成功 → 提示"登录成功" + 回调关闭页面 + 结束循环
        · 失败 → 记下凭证与时间，解锁，继续循环

必须有的两个保护：
  1) 在途锁：校验期间不再轮询，同时把「手动保存」按钮置灰。
     否则自动校验与用户手动点保存会并发写库、重复弹"登录成功"。
  2) 暂停条件：手动弹窗打开中暂停轮询（isPaused 每次循环重新读取最新值）。

实现注意：
  - 承载这段逻辑的组合函数必须在组合体顶层「无条件」调用；
    放进条件分支会导致轮询反复重启。
  - 捕获异常时，CancellationException 必须原样抛出（协程取消语义），
    其余异常一律吞掉按"本轮无效"处理。


六、手动兜底（必须有，且要有两条）
----------------------------------------------------------------
自动检测不可能 100% 可靠（页面改版、跨域 Cookie、风控弹窗、结构变化），
所以必须保留手动通路：

  1) 「保存」按钮
     - 用当前 WebView 里的凭证，走一遍和自动检测完全相同的校验+落库路径。
     - 用户看到自动检测没动静时，可以自己点一下。

  2) 「手动粘贴凭证」入口
     - 弹窗让用户粘贴完整 Cookie 串（或 Token）。
     - 同样走同一校验入口。
     - 这是最后的保命通道：WebView 完全读不到时仍能登录。
     - 弹窗里要提示需要包含哪些关键字段。

  3) 文案与引导
     - 首次进入登录页弹一次简短教程：在网页里登录 → 自动检测 →
       若没自动登录点「保存」→ 或粘贴 Cookie。
     - 用户不需要知道技术细节，但要知道有退路。


七、校验与落库
----------------------------------------------------------------
- 校验通过后持久化：平台标识 + 凭证 + 昵称 + 更新时间。
- 建议加密存储（凭证等价于账号密码）。
- 落库后重置「刷新计时」，避免刚登录就触发一次无谓的会话刷新。
- 暴露一个可观察的登录态（Flow）给主页和登录页共享。


八、会话保活
----------------------------------------------------------------
- 部分平台的登录 Cookie 会随时效缩短或随响应被替换：
  1) 响应回写：每次接口响应若带 Set-Cookie，把相关字段合并进已存凭证并回写。
     合并用独立的 IO 作用域，不要阻塞请求链路。
  2) 定时刷新：记录上次刷新时间，超过阈值（例如 90 分钟）时用一个
     轻量接口重新触发凭证下发；刷新失败要回退用旧的（不要让业务直接崩）。
- 错误示范：只在首次登录时取一次凭证，之后永不更新 ——
  短期能用，跨过有效期后所有请求开始 401/412。


九、退出登录
----------------------------------------------------------------
- 清理 WebView 侧：removeAllCookies(null) + flush()。
- 清理本地存储：删除该平台凭证、清除已登录标记。
- 两步都要做，只清一边会导致"退了但还能用"或"登录了又要重登"。


十、常见误判与坑（清单）
----------------------------------------------------------------
1) 把「Cookie 出现」当「登录成功」→ 假登录。
2) 判定语义写反（任一命中 vs 全部命中）→ 误判或永远判不了。
3) 某平台判定字段列表留空 → 该平台永远登录不成功（界面卡在轮询）。
4) WebView 不设 UA → 走到移动版页面 / 与接口 UA 不一致被风控。
5) 不设第三方 Cookie → 读不到跨域凭证。
6) 只做自动检测，没有手动兜底 → 失手时用户无路可走。
7) 无节流与同凭证重试限制 → 高频打接口，可能被限流。
8) 无在途锁 → 自动校验与手动保存并发写库、重复弹成功提示。
9) shouldInterceptRequest 里阻断了请求（返回非 null）→ 页面直接打不开。
10) 轮询逻辑放在条件分支里 → 反复重启，状态错乱。
11) 页面销毁不 destroy() → 内存泄漏。
12) 退出登录只清一边 → 状态不一致。
13) 把加载态/校验在途态混成一个布尔值 → 按钮禁用逻辑错乱。


十一、各平台判定字段（事实层，供定义判定规则用）
----------------------------------------------------------------
以下只列「判定登录态需要哪些字段」这一客观事实，不含实现：

  夸克：需要同时存在 __pus 和 __puus 两个字段。
        （只判其中一个会把登录中间态误判成已登录。）
        __puus 有时效（约 3 小时），需要按第 8 节的保活机制处理。

  UC  ：与夸克同构，同样需要同时存在 __pus 和 __puus。

  百度：判定字段是 BDUSS（登录凭证）。
        另有 STOKEN 配合使用，另有 bdstoken 是接口令牌（可缓存），
        不要和登录凭证混为一谈。

  迅雷：登录后走 access_token 体系（JWT，含 exp / sub），
        凭证本身不是普通 Cookie，需要按 Token 方式存储与刷新。

结论：每个平台的判定规则必须单独定义，不要共用一套。


十二、落地检查清单
----------------------------------------------------------------
实现完成后逐条自检，全部为「是」才算合格：

  [ ] WebView 开启了 JS + DOM 存储
  [ ] WebView 显式设置了该站点桌面网页版 UA
  [ ] 桌面版页面可缩放、viewport 正常（必要时注入 viewport）
  [ ] 开启了 setAcceptCookie 与 setAcceptThirdPartyCookies
  [ ] 主途径按「多个 URL 列表」读取 Cookie 并去重合并
  [ ] 兜底途径拦截请求头采集，且返回 null 不阻断请求
  [ ] 兜底采集使用线程安全容器
  [ ] 每个平台单独定义了判定字段与判定语义（任一 / 全部）
  [ ] 四个平台的判定规则都不是空列表
  [ ] 登录判定包含「网络校验」环节，而非只看 Cookie 存在
  [ ] 校验失败按中间态处理：不报错、继续轮询
  [ ] 轮询有节流（校验最小间隔）与同凭证重试限制
  [ ] 校验在途时有锁，且会禁用「保存」按钮
  [ ] 手动弹窗打开时暂停轮询
  [ ] 提供了「保存」按钮手动兜底
  [ ] 提供了「手动粘贴凭证」兜底
  [ ] 首次进入有简短登录教程
  [ ] 校验通过才落库，落库建议加密
  [ ] 落库后重置刷新计时
  [ ] 响应 Set-Cookie 会合并回写凭证
  [ ] 有按有效期的定时刷新，失败回退旧凭证
  [ ] 退出登录同时清 WebView Cookie 与本地存储
  [ ] 页面销毁时 destroy() WebView
  [ ] CancellationException 原样抛出，其余异常吞掉
